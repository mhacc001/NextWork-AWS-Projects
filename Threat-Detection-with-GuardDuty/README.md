# Threat Detection with GuardDuty

## Overview

In this project, I deployed a deliberately vulnerable web application (OWASP Juice Shop) on AWS using CloudFormation, then played both attacker and defender to see how real-world cyberattacks unfold and how Amazon GuardDuty detects them.

As the attacker, I exploited SQL injection and command injection vulnerabilities to bypass authentication, steal AWS IAM credentials from the compromised EC2 instance, and use those stolen credentials from AWS CloudShell to exfiltrate sensitive data from an S3 bucket. As the defender, I then analyzed the GuardDuty finding generated by that activity to understand how the threat was detected and what information it revealed about the attack.

## Services Used

- **AWS CloudFormation** — deployed the vulnerable web app infrastructure as code
- **Amazon EC2** — hosted the OWASP Juice Shop web application
- **Amazon S3** — stored sensitive data targeted in the attack
- **Amazon CloudFront** — distributed the web app publicly
- **AWS CloudShell** — used to simulate an external attacker session with stolen credentials
- **Amazon GuardDuty** — provided machine learning-based threat detection and generated the finding

## What I Did

### 1. Deployed the Web App
Used a CloudFormation template to stand up a full environment: an EC2 instance running OWASP Juice Shop, supporting VPC/networking resources, a CloudFront distribution, an S3 bucket holding a simulated sensitive file, and a GuardDuty detector for monitoring.

Once deployed, I located the stack's Outputs, including the public JuiceShopURL used to access the app for the rest of the project.

![CloudFormation Outputs](./Screen%20Shot%202026-08-15%20at%2011.43.19%20AM.png)

### 2. Logged In and Bypassed Authentication (SQL Injection)
Opened the deployed Juice Shop app and used a classic SQL injection payload (`' or 1=1;--`) in the login email field to bypass authentication and log in as an administrator without valid credentials.

![Juice Shop Landing Page](./Screen%20Shot%202026-08-15%20at%2011.44.13%20AM.png)
![SQL Injection Login](./Screen%20Shot%202026-08-15%20at%2011.46.11%20AM.png)
![Admin Login Success](./Screen%20Shot%202026-08-15%20at%2011.46.41%20AM.png)

### 3. Stole IAM Credentials (Command Injection)
Injected a malicious JavaScript payload into the admin profile's Username field. The unsanitized input was executed by the server, which queried the EC2 instance metadata service and wrote the instance's temporary IAM credentials to a publicly accessible file within the app.

![Command Injection Result](./Screen%20Shot%202026-08-15%20at%2011.50.35%20AM.png)
![Stolen Credentials Exposed](./Screen%20Shot%202026-08-15%20at%2011.53.42%20AM.png)

### 4. Exfiltrated Data via CloudShell
Using AWS CloudShell (which runs under a separate, temporary AWS account ID), I downloaded the stolen credentials.json file and confirmed its contents before configuring a new AWS CLI profile with them.

![Downloading and Viewing Stolen Credentials](./Screen%20Shot%202026-08-15%20at%2012.14.23%20PM.png)

I then used the stolen profile to copy and read a sensitive file from the target S3 bucket — successfully exfiltrating data using credentials that were never meant to leave the EC2 instance.

![CloudShell Full Attack Chain](./Screen%20Shot%202026-08-15%20at%2012.20.42%20PM.png)

### 5. Detected the Attack with GuardDuty
Switched to the defender role and reviewed GuardDuty's findings. Within about 13 minutes of the CloudShell activity, GuardDuty flagged a **High severity** finding: `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.InsideAWS`. The finding correctly identified that credentials scoped to a specific EC2 instance role were being used from a different, remote AWS account — exactly the anomaly created by using the stolen credentials in CloudShell.

![GuardDuty High Severity Finding](./Screen%20Shot%202026-08-15%20at%2012.33.05%20PM.png)

## Key Takeaways

- **SQL injection** exploits unsanitized input in database queries to bypass authentication or manipulate data, and can be as simple as a single crafted string in a login field.
- **Command injection** occurs when an application executes attacker-supplied input as code rather than treating it as plain data — in this case turning a "username" field into a remote code execution vector.
- **EC2 instance metadata credentials** are powerful and dangerous if exposed: anyone who obtains them can act with the full permissions of that instance's IAM role from anywhere.
- **AWS CloudShell's temporary account ID** made it possible to realistically simulate an external attacker even while using my own AWS account, since GuardDuty could distinguish the "instance's own usage" of its credentials from usage originating in a different account.
- **GuardDuty's anomaly detection** doesn't rely on static rules alone — it learns a resource's normal behavior (like which account and location typically uses a given instance's credentials) and flags meaningful deviations, in this case within about 15 minutes of the suspicious activity occurring.
- Detection findings like `InstanceCredentialExfiltration.InsideAWS` provide actionable forensic detail: the exact API call made, the resource targeted, the access key used, and the location/account of the caller — all critical for incident response and root cause analysis.
